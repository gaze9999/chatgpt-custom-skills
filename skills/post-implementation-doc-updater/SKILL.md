Codex context brief。未有實作證據時請先索取。---# Post-Implementation Doc Updater本技能在實作變更完成後更新既有文件與 memo，目的在於對齊 README、Markdown note、Notion memo、changelog、API 參考與 Codex context brief，確保與實際 code 變更一致。它不是用來從頭撰寫新文件；目的是基於具體實作證據，識別受影響文件並只做必要更新。## Subagent delegation僅委派可獨立驗證的子任務，如證據複核、目標檔案盤點、特定格式檢查。子任務交接需包含實際 diff/commit/檔案，與已驗證事實、約束、預期結果與停止條件；不要傳遞完整對話。## Strict activation requirements僅在三條件滿足時啟用：1. 使用者明確要求更新、對齊、同步現有文件或 memo。2. 有可引用的實作變更證據：diff、commit、PR、release、migration、變更檔清單、完成的 refactor、或貼上的 code-change 總結。3. 至少能指出一個文件目標（repo Markdown、README、docs、changelog、API 參考、Notion 頁或 Codex context brief）。不要因為對話中出現 `Notion`、`docs`、`Markdown`、`memo`、`API`、`Codex` 或 `sync` 就使用本技能。若證據不足，先要求 diff / commit / PR / release / migration note / changed-file list / code-change summary；若可用另一專門流程直接完成，則不要誤用本技能。## When to use this skill當使用者要求依實作證據更新既有文件時使用，例如：- git diff、commit、branch、PR、release、變更檔清單- 已完成功能、Bug 修正、migration、重構、設定變更- API 契約、request/response、CLI 命令、環境變數、安裝部署行為有更新- 使用者可見行為改變需要更新 README/docs/memo/Notion/changelog/brief## When not to use this skill不要用於：- 純 Notion 頁面整理、資料庫清理、分類重排- 無實作證據的文件撰寫、改寫、校正、摘要、翻譯- 一般 Notion 與 Markdown/Notion 雙向同步（未與變更綁定）- 直接 coding、除錯、重構、實作- 將需求轉成 coding 任務 prompt- 實作前將規格轉成 context brief- 製作正式 PDF/DOCX/Markdown 交付檔案- 一般會議紀錄、研究筆記或普通解釋## Ambiguous request handling遇到需求重疊時，採較嚴格路由：- 規格/API 說明 + 未來實作前的摘要 → Codex Context Brief Builder- 要成品文件（PDF/DOCX/Markdown）→ Document Production Pipeline- Notion 頁面或資料庫整理 → 對應 Notion 工作流- 單一 coding 任務需求 → Coding Task Prompt Builder- 有實作 diff/PR/commit 需更新文件 → 本技能若只講「更新文件/同步 Notion」但未提供變更證據，請先確認缺少的證據與目標，不可直接假設。## Inputs接受的證據來源：- repo diff、commit、branch、pull request、release notes、變更檔清單- 貼上的 code-change summary- 現有 Markdown/docs/README/changelog/memo/Context brief- 只在使用者明確要求 Notion 更新時，才包含 Notion 頁/資料庫- 上傳 PDF 僅作為 optional 證據，不可視為同步目標證據不足時，只追問影響正確性、目標、或授權所必需資訊。## Evidence confidence1. Diff 摘錄與變更檔：最高可信2. PR/commit＋變更檔：高可信3. release/migration note 且可對應程式變更：中可信4. 僅使用者摘要：可用，但標示為 summary-based不支持未驗證 claim；只有在 user summary 可用時明確標示為 summary-based。## Change impact rules需要更新文件的情況：- public API、endpoint、SDK、CLI、schema、event、整合行為改變- 使用者可見行為、UI 狀態、驗證、文案、流程、可及性、權限改變- 安裝、設定、執行、部署、環境變數、遷移步驟改變- 破壞性變更、相容性限制、風險、棄用、已知限制- 已有文件中對架構、檔案結構、模組邊界、agent/自動化行為的描述需同步通常不更新的情境：- 內部重構但行為無差異- 只改測試、格式、lint 或變數名稱- 版本或相依調整但不影響可觀測行為- 非使用者面對的產物檔不確定則標記 `maybe`，補註缺漏證據。## Notion update gate不要因提到 docs/note/sync 而大範圍讀寫 Notion。若允許 Notion 更新，需先依 [Notion Sync Reader and Writer Contract](references/notion-sync-reader-writer-contract.md) 讀取精準目標；上傳的 JSON snapshot 僅可本機閱讀，不等同 live 寫入授權。僅在以下情況才更新 Notion：- 使用者明確要求更新與這次變更對應的 Notion 頁/項目- 使用者提供明確 Notion 目標，或上下文已含明確目標- Markdown 前置元資料有明確關聯，例如 `notion_page_id`若未明確要求，保留 Notion 不動，回報只更新 repo/Markdown。## Notion and Markdown dual-update rule預設不做雙向更新。僅在以下任一條件才同步兩邊：- 明確要求同時更新 Notion 與 local Markdown- 同時提供 Notion 與 Markdown 目標- 目標 Markdown metadata 明示 `sync_mode: bidirectional`若僅一方有要求，更新該方並說明另一方未動。若兩邊皆有既有變更，不可直接覆蓋，需先產出衝突說明與後續方向。## Canonical source strategy有雙向同步時優先 repo Markdown 為 canonical source：1. 優先更新 repo Markdown / docs2. 僅在通過條件時同步摘要到 Notion3. 保持語意一致，不要求格式完全一致4. 保留 Notion page ID、frontmatter、source link、last-synced metadata若使用者指定 Notion 為主體，則以 Notion 為主體來源並註明。## Recommended workflow1. 確認證據、更新目標與寫入範圍2. 若證據不足，不進行本技能；先要證據3. 可用腳本時先跑 `scripts/scan_changed_files.py`4. 非平凡更新時參考 [Doc Update Rules](references/doc-update-rules.md)5. 將變更檔分為 `yes` / `maybe` / `no`6. 只閱讀必要 diff 與現有段落7. 先產出最小更新計畫8. 只更新必要 doc/memo/changelog/Notion/context brief9. 有計畫時可執行 `scripts/validate_doc_update_plan.py`10. 回報已改文件、未改項目、未決事項、驗證結果## Deterministic helper scripts變更掃描：```bashpython scripts/scan_changed_files.py --repo <repo-root>```掃描指定 diff：```bashpython scripts/scan_changed_files.py --diff-file <diff.patch>```更新計畫驗證：```bashpython scripts/validate_doc_update_plan.py <doc-update-plan.md>```可用 JSON 輸出：```bashpython scripts/scan_changed_files.py --repo <repo-root> --jsonpython scripts/validate_doc_update_plan.py <doc-update-plan.md> --json```## Sync target readers and writers雙向更新前先檢閱 Markdown 目標：```bashpython scripts/inspect_markdown_sync_target.py <target.md> --json```Reader 僅回報該檔的 SHA-256、frontmatter、標題結構、Notion page id/url、`sync_mode`，不掃目錄、不寫入。要替換 Markdown 目標時，先取 hash 後以 UTF-8 檔準備完整新內容，先 dry-run 再正式寫入：```bashpython scripts/write_markdown_sync_target.py <target.md> --content-file <replacement.md> --expected-sha256 <reader-sha256> --dry-runpython scripts/write_markdown_sync_target.py <target.md> --content-file <replacement.md> --expected-sha256 <reader-sha256>```Notion snapshot 檢閱：```bashpython scripts/inspect_notion_sync_target.py <uploaded-notion-snapshot.json> --page-id <optional-page-id> --json```如果是 live Notion 更新，需先通過 Notion gate，依 [Notion Sync Reader and Writer Contract](references/notion-sync-reader-writer-contract.md) 導向單一目標：- `read` 精準目標- 做最小變更- 立即 `re-read` 目標確認未經授權不得模擬 Notion client 或儲存 token。明確為只增量 append 的 Notion 更新且已有授權時，寫入指令類型如下（僅 page-id、blocks JSON、last-edited-time、環境變數 token）：```bashNOTION_TOKEN=<environment-only-token> python scripts/write_notion_sync_target.py --page-id <page-id> --blocks-file <prepared-blocks.json> --expected-last-edited-time <reader-time> --dry-runNOTION_TOKEN=<environment-only-token> python scripts/write_notion_sync_target.py --page-id <page-id> --blocks-file <prepared-blocks.json> --expected-last-edited-time <reader-time> --json```若以 PDF 作為 optional 證據，先做萃取：```bashpython scripts/inspect_pdf_sync_source.py <uploaded.pdf> --max-pages 20 --jsonpython scripts/inspect_pdf_sync_source.py <uploaded.pdf> --max-pages 20 --ocr-fallback --ocr-lang eng --json```PDF reader 回報 source SHA-256、頁數、萃取範圍、頁面文字與 OCR 引擎；OCR 以 `rapidocr` + `onnxruntime` 為第一步，失敗才視情況轉 Tesseract，且 OCR 文字只為有限證據，不代表完整版面或表格/手寫/戳記/圖像語義已完整驗證。腳本限制：- changed-files scanner 只提供可能影響的路徑推斷，不保證行為真的改變- plan validator 檢查結構與風險標籤，未保證每一 claim 都被 diff 完整支撐- markdown reader 僅讀取指定檔案，不能授權 Notion 權限- markdown writer 為全檔替換式且受 hash 保護，不會合併同時變更- Notion reader/writer 受 connector 與權限限制- OCR 為 optional；首次使用可能下載模型，OCR 文字保留信心值但仍非完整證據- 發現 WARN 須先 review 後才套用## Update plan structure對超過單一檔的更新，使用以下精簡計畫：```markdown# Post-Implementation Doc Update Plan## Activation gate- Existing doc / memo update requested:- Implementation-change evidence present:- Target surface identified:- Notion explicitly in scope:- Dual Notion / Markdown update authorized:## Change evidence- Source:- Range / commit / PR:- Evidence coverage:- Evidence confidence:## Impact summary| Area | Impact | Evidence | Doc action ||---|---|---|---|## Target updates| Target | Action | Reason | Status ||---|---|---|---|## No-update decisions| Change | Reason docs are not updated ||---|---|## Notion / Markdown sync- Canonical source:- Markdown target:- Notion target:- Dual-update authorization:- Conflict handling:## Risks and unresolved items- Open question:- Assumption:- Conflict:```## Writing rules- 每一重要更新都要對應可見的實作證據- 不把內部實作細節推為公開保證，除非該行為本來就屬於公開契約- 明確標記 breaking change、migration、相容限制、棄用、營運風險- 保留精確的 API 名稱、config key、路徑、命令、版本條件- 保持精簡，必要時只更新 changelog/memo，不添冗長敘述- Notion 與 Markdown 並行有差異時，不盲目覆蓋，先提出衝突說明- 不新增秘密、token、憑證或非必要個資## Final response最後回覆精簡，包含：- 使用的實作證據- 實際更新的 doc/memo target- 不更新但有必要提及的原因- Notion / Markdown 同步結果（是否雙向授權）- 驗證結果與未驗證項目
